# 项目管理

独立的 asHub 插件。根据用户需求规划成员职责，选择真实可用的模型、思考强度和 VPN 配置，按用户的宿主授权设置创建项目或对话，也可修改已有对话配置、移出项目、归档或永久删除。

## 安装

需要带有 `ashub:catalog` / `ashub:execute` **v1** 通用接口的 asHub 构建；0.2.0 新操作还要求 catalog.operations 提供 conversation.update/detach/archive/delete；此前发布的 0.20.9 不包含这些接口。仅安装插件不能给旧客户端补上宿主能力。

支持快速安装的 asHub 可在「插件 → 安装插件」中选择此插件 ZIP，确认安装后重启。也可手动将本目录复制到 `~/.agent-sh/extensions/项目管理/`（Windows：`%USERPROFILE%\.agent-sh\extensions\项目管理\`），保留 `index.mjs` 和 `package.json`。重启 asHub 或新建对话，在插件菜单确认启用。无需 npm install、API 密钥或插件配置。

## 使用

例如：

> 为当前项目建立三个成员，分别负责文献检索、数据分析和审校。根据任务选择模型，VPN 继承全局。先让我确认，再创建。

或：

> 在 /Users/me/research 新建一个研究项目，将当前对话作为协调者，再规划项目成员。

插件先读取项目和模型目录，再显示待确认的操作。项目与成员分两次确认；已有项目只需确认成员方案。一次最多 12 个成员，可分别选择名字、职责、模型、思考强度、VPN 和项目。独立对话必须指定现有绝对目录；项目内新对话使用项目根目录。

职责说明作为对话说明持久保存。创建不会自动开始模型回复、发送任务或继承当前对话历史。开展工作需用户授权，可复用 asHub 的同项目对话通信。加入新项目时，当前对话会从原项目移出，授权预览会列出该对话。

## 授权和失败处理

- 默认由宿主展示目标及具体参数并等待本次确认。新版宿主支持在插件配置中开启自动批准；全局工具自动批准开关不决定本插件的授权。
- 拒绝、取消或 5 分钟未确认，均不执行变更。
- 相同 requestKey 的重复调用复用结果；改变参数必须使用新方案，由宿主重新校验授权。
- 成员逐项创建。失败时保留已经创建的对话并报告结果，不自动删除用户资源。
- 程序意外退出后，执行状态不确定的请求不会自动重放；先查看现有对话再决定下一步。
- 卸载插件不会删除已经创建的项目、对话和职责说明。

插件与宿主扩展同进程运行，适用于可信插件，不是用于隔离恶意代码的安全沙箱。

## 管理已有成员

先读取目录中的 `conversations`，使用真实 ID。可要求：

> 把审校成员改名为终审，思考强度改为该模型支持的最高级，VPN 关闭，先让我确认。

> 将检索成员移出项目，保留对话。另将已完成的数据成员归档。

- 修改：名称、模型及 provider、思考强度、VPN（开启/关闭/继承）。未提供的字段保留；切换模型而未指定思考强度时重置为模型默认值。工作目录和职责说明暂不支持修改。
- 移出：回到独立会话列表，保留历史和原目录。
- 归档：移出项目并保留历史，可手动从归档恢复。
- 永久删除：删除对话历史和上传附件，无法撤销，不删除工作目录里的文件。
- 目标必须是空闲的未归档对话；不允许归档或删除发起操作的当前对话。归档后的管理通过应用归档界面完成。
- 等待授权期间目标配置、项目归属或活动发生变化，旧方案失效，需要重新查询后提案。失败可能已部分生效，先检查结果，不盲目重试。


## 协作交付（0.3.0）

新版宿主提供 `ashub:collaboration:wait` 和 `ashub:collaboration:deliver` 时，插件启用团队交付约定；旧宿主仍保留原有创建和管理功能。仅升级插件不会给旧桌面端补上通信接口。

1. 协调者通过 `conversation_send` 分派已获授权的任务，记录返回的 taskId。
2. 用 `conversation_wait({targets:[{id:taskId}, ...]})` 一次等待多个任务（默认最多 120 秒），任意一个结束即返回。下一次将返回的 `cursors`（包含状态与版本）原样作为 `targets`；`hasMore:true` 时用这些游标和 `waitMs:0` 继续读取，避免漏掉本批尚未返回的交付；超时只带简短状态，不复制过程文本，不自动催问成员。
3. 成员在对应任务结束前使用 `conversation_deliver` 提交 `summary`（结论与验证）、`artifacts`（label/path）、`unresolved`。引用不自动读取，不改变权限；此操作不会唤醒协调模型，也不会把任务标记为完成。
4. 协调者优先检查状态和明确交付；没有交付时返回 `delivery:null`，可用旧 `conversation_task` 分页读取完整文字。失败、中断、取消仍按原状态报告，不能因存在交付就当作成功。

项目分工和交付约定由本插件提供，任务等待、权限检查、游标及结果存储由宿主通用接口完成。不自动共享完整历史、不自动互相回信。

0.3.1 补充批量交付分页约定。宿主会保留未返回结果的游标，并区分异常重启前后的任务状态，避免遗漏结果。

## 任务补充（0.4.0）

新版宿主提供 `ashub:collaboration:supplement` 时，插件增加两个工具：

- `project_management_supplement({id, requestKey, message})`：`id` 是自己通过 `conversation_send` 派发任务得到的 taskId。纠正方向、补充关键材料或修改约束时使用；把相关要求整理成一条，不逐句打断。
- `project_management_supplement_status({id, requestKey})`：只查询投递回执，不发送消息、不启动模型。

任务未开始时，补充追加到原来的队列位置；任务执行中，在下一次模型请求前送入，不中断当前工具或网络请求；任务已结束时返回 `task_ended`，不会偷偷再启动一轮。独立的新任务仍用 `conversation_send` 正常排队，不伪装成补充。此能力需要包含新通用接口的 asHub 构建，仅安装插件无法让旧发行版获得该接口；旧宿主仍可使用原有项目管理及协作功能。

示例：先派发“统计年度数据”，取得 taskId；随后发现口径变化，要求“给这个任务补充：排除 2023 年，其他口径保持不变”。插件使用原 taskId 和新的稳定 requestKey 提交。重复调用同一 key 和同样内容不会重复发送，修改内容必须使用新 key。每个任务最多 32 次补充，排队合并内容最多 64,000 字符。

`pending` 表示等待送入；`consumed` 只表示进入模型上下文，不代表已经执行或验证；`modified` 表示用户编辑过待发送内容；`dropped/rejected/interrupted/uncertain` 均不能视作送达，不自动换 key 重发。发生工具错误先查询同一 key 的回执。重启后的未确认投递标记 interrupted，不会重放。

补充不创建第二个协作任务。补充进入上下文后，旧的明确交付会失效，成员需通过 `conversation_deliver` 重新交付，协调者再核查。成员遇到无法继续的关键问题，应在 unresolved 中写明问题和选项、交付已完成部分后结束任务；协调者通过原有批量等待收到结果，再处理依赖。没有新增轮询器、自动催问或无限自动调度。

本插件仍不能提供独立新任务的跨调用去重、强制中断工具或修改已经被模型消费的消息。创建、修改、删除成员始终通过宿主授权接口执行。

独立协作任务不能通过队列“插队”按钮混入另一个任务的执行轮次；宿主会提示改用任务补充，以免任务回执失去归属。普通用户消息的插队不受影响。

## 按一次工作组织协作（0.5.0）

例如：“让数据成员和文稿成员分别核查表 2，等两份结果验收后再交给复核成员。返工只处理发现的缺口。”
协调对话通过 project_work_plan 记录本次目标及 1–12 个步骤；每步有负责人、交付物、验收条件与依赖。可同时开展没有依赖的步骤。独立短任务可继续直接发送。

project_work_brief 返回可直接交给 conversation_send 的参数。原样发送后，插件根据实际发送事件自动登记 taskId。状态记录本身不发送消息，不创建成员或提升权限。工作完成后先通过 conversation_wait 或 project_work_status 查看真实交付，再使用 project_work_review 写明验收依据。只有 accepted 可解锁下游；revise 或 blocked 保留此前成果，后续使用 previousTaskId 只补缺口。若下游需要文件，在验收理由中附上可用的路径。没有明确交付时应核对原始任务记录。

工作按当前项目和协调对话隔离。重开同一协调对话后，可直接询问“上次还有哪些步骤待验收”。receipt_pending 表示已准备说明但没有登记发送回执；核实原始调用，已发则用 project_work_link 补登记。只有确认未曾发送时才从步骤详情取回原说明发送。无法确认时保留待核对状态。该机制不保证独立发送恰好执行一次。

此功能需要宿主提供 catalog/wait/deliver 和带 node:sqlite 的运行时。记录存储在插件的 profile 数据目录；旧版 asHub 通过插件菜单安装时也支持，不写入项目工作树。

## 自动授权

支持此设置的新版 asHub 可在「插件 → 编辑配置」中开启「自动批准操作」。
默认关闭。开启后，该插件后续发起的宿主操作无需逐次确认，包括项目与对话修改以及永久删除。设置立即生效，关闭后恢复确认。
已经弹出的授权卡仍需处理；页面检查、取消和操作校验继续执行。

## 阻塞通知（0.6.0）

成员遇到必须由原协调者决策的问题时，可用 `project_management_blocked`，提供当前 Task ID、稳定 requestKey、具体问题、已核对的证据和推荐方案。普通进度和成果仍通过交付机制返回，不占用插队通道。

- 协调者忙碌：在下一次模型请求前接收，不打断工具或正在进行的模型请求。
- 协调者正在等待成员：提前返回 `attention`，让当前轮次接收通知，即使它正在等待另一位成员。
- 协调者空闲：正常唤醒；已停止的对话不自动唤醒。发送期间若另一轮刚开始，则安全排队。
- 相同 requestKey 不重复发送；相同内容换 key 也不会重发。每任务最多 8 次、不同问题间隔至少 60 秒、每协调者每分钟最多 6 次，且每任务只能有一条未确认送达的通知。
- `project_management_blocked_status` 只查回执。`consumed` 不代表已经决策；失败、不确定、撤回和重启不自动重发。

成员通知后继续可独立完成的工作；确实无法推进时，将问题写入 `unresolved` 并交付当前成果、结束任务，避免双方互相等待。协调者先检查任务最新状态，不自动回复“收到”或重复派发原任务。通知不授予新的操作权限。

需要支持 `ashub:collaboration:signal` 的新版宿主；旧宿主不会显示这两个工具，原有项目管理功能保持可用。升级插件后，请在当前任务结束后完全退出并重启 asHub。
